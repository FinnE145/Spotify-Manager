## Overview
**Symr** (**S**potif**Y** **M**anage**R**, pronounced "simmer") — a web-based music library manager.

A Flask app for maintaining and verifying a Spotify library that follows a specific set of personal conventions (an append-only "Finn All" master playlist, semver-named "current favs" playlists, an ATG playlist, and a CI/CL intake playlist). The full library/usage spec lives in `docs/library_spec.md` (TBD).

## Tech Stack
- **Python 3.14.5** (fall back to 3.12 if something doesn't work), **Flask**.
- **Spotipy** for Spotify Web API access — handles OAuth, token refresh, and paging.
- **SQLite** via the stdlib `sqlite3` + a thin helper (no ORM unless the schema forces it): library snapshot, version history, folder-structure record, cover library, canvas boards, etc.
- **Frontend:** server-rendered **Jinja templates + vanilla JS**, no SPA framework. Richer interactive JS only where a feature needs it (e.g. the org canvas) — settle those specifics in that feature's spec.
- **Env:** `venv` + `requirements.txt`.
- v1 is read-only. Fill in remaining choices (charts, etc.) as features are specced. Never assume an unstated version or library.

## Codebase Map
- `docs/` — specs and reference. Feature specs at `docs/specs/<feature>.md`; per-feature extra files (sub-specs, notes, verification reports) in `docs/<feature>/` — including `docs/scoring/tuning_prototype.py`, which is not a note but the **executable reference** for the scoring algorithm: it produced every parameter in `scoring-H.md` §10.1, and an implementation that disagrees with it is wrong, or it is; planning docs in `docs/Planning/`; hard Spotify API limits in `docs/spotify_constraints.md`.
- **"The roadmap" always means `docs/Planning/roadmap.md`** — the standing, ordered plan of what gets built next. Each lettered step becomes its own `/symr-plan` session and its own spec; landed steps stay, marked ✅ DONE and pointing at the spec that is authoritative for what actually shipped (read that spec, never the roadmap summary, before touching landed work). It also carries dated measurements that shouldn't be re-derived. Its sibling `docs/Planning/feature_ideas.md` is the loose backlog the roadmap draws from — ideas, not commitments.
- `app.py` — Flask app factory. Page routes (`/` home, `/canvas`, the **entity pages** `/song/<id>` / `/version/<id>` / `/recording/<id>` / `/release/<id>` (four `@app.route` decorators on **one** view function, each supplying its tier) / `/track/<id>` / `/album/<id>` / `/artist/<id>` / `/playlist/<id>` (`?generation=1` renders the generation view, `?tier=` toggles it) / `/search`, `/dev` dev-tools landing, `/dev/snapshot`, `/dev/canonical*`, `/dev/artists`, `/dev/import`, `/dev/roundtrip`, `/dev/generations*` (including the plain form-POST `/dev/generations/confirm` — still a real form POST with no fetch, though `generation_confirm.js` now adds click feedback over it), `/dev/scoring`, and stubs `/audit`, `/covers`, `/folders`, `/analytics`), OAuth (`/login`, `/callback`), `/api/*` endpoints, **three** app-wide `before_request` hooks in order — `api_log.api_context` (first, and unconditional: the login guard below calls `get_spotify_client()`, which can itself fire a token-refresh POST that must already be labelled), then the login guard (exempts `login`/`callback`/`static`), then `scoring.ensure_fresh()`, deliberately one hook rather than scattered per-route like `canonical.ensure_track_groups()`, since a single hook is the one write path that can't be forgotten — one `@app.context_processor` exposing `scoring_failed` / `scoring_error` from `scoring.recompute_status()`, which is how a *background* recompute failure gets seen at all now that it has no request to 500 (`base.html` renders the banner), `_LISTING_CAP` / `_cap_listing` (`/dev/canonical`'s two listings render 50 rows on an unfiltered load and *all* matches once either filter — `?q=` for groups, `?cross=` for cross-artist — is set, so searching `%` still gets the whole thing), and centralized error handlers (`HTTPException` + `Exception`) that render `error.html` for pages and JSON for `/api/*`.
- `config.py` — every setting, read from the environment via `.env` (python-dotenv): Spotify credentials / redirect / scopes, `DB_PATH` (`SYMR_DB_PATH`), the spotipy token-cache path, `APP_PORT` / `APP_DEBUG`, `MAX_CONTENT_LENGTH`, and `SECRET_KEY` (random per process unless `SYMR_SECRET_KEY` is set, which is what keeps sessions valid across a restart). Credentials live in the environment only — never hard-code or log them.
- `spotify_client.py` — the only place an authed Spotify client is built: `get_auth_manager()` (OAuth, scopes from config, on-disk token cache) and `get_spotify_client()` (returns `None` when there's no valid cached token). Its custom `requests` session sets `respect_retry_after_header=False` so a 429 raises immediately instead of blocking for an hours-long app-quota `Retry-After` — `snapshot.py`'s `_call()` handles the wait itself. Scopes are read-only. Both session builds instantiate `api_log.LoggingSession`, and deliberately **two separate instances**: sharing one would apply the API client's GET-only retry policy to `SpotifyOAuth`'s token-refresh POSTs, changing auth behaviour to get logging.
- `api_log.py` (`docs/specs/partial-pulls-J.md` §4) — the API request log. `LoggingSession` overrides `requests.Session.request()`, so **every** outbound Spotify request gets an `api_request` row regardless of caller, including the entity pages' detail fetches that never go through a job — hooking the session rather than `jobs.call` is what makes that true. `api_context` is a **contextvar, not a module global**: a job's background thread and a page-load thread run concurrently, and a global would let one overwrite the other's label. `record()` opens its own connection per write (no `check_same_thread`, no lock, ~1.5ms against a 100ms+ request) and **swallows every exception — a logging failure must never break the request it is logging**, which also means a lost row is silent, so no job may hold an open write transaction across a Spotify request (see `snapshot._pull_liked_songs`). Stores **no headers, no bodies, no response content** — only `Retry-After` by name into its own column and `len(response.content)` as an integer. `request_counts()` is the `/dev` row's two rolling counts, filtered to `host = 'api.spotify.com'` so token refreshes don't inflate the quota picture.
- `jobs.py` — the one background-job slot. A single module lock guards a single `_active` job name, so claiming the slot is one atomic check-and-set (`try_start`) with no lock ordering and no race — `snapshot.py` / `history_import.py` / `roundtrip.py` / `backfill.py` no longer own job locks of their own. Also owns cooperative stopping (`request_stop` / `stop_requested` — a flag the job polls at its own safe points, never a kill; all four jobs now poll it), sets `api_log.api_context` to the job name in `try_start`'s `run()` wrapper, `now_iso()`, the `RateLimited` fail-fast wrapper `call(status, fn, …)` that every Spotify request in every job goes through, and `JobStatus` (per-job progress fields + a capped 200-entry event log; `running` is *derived* from `jobs.active()`, never stored).
- `db.py` — SQLite `SCHEMA` + additive migrations (`_migrate`) + `VIEWS`. Library metadata is normalized: `track`, `album`, `artist`, plus `track_artist` / `album_artist` join tables carrying per-credit `position`; each of `track`/`album`/`artist` also keeps a verbatim `raw_json` of the Spotify object. `membership` is the append-only per-playlist log; `snapshot` is per-playlist state (including the `excluded` flag that skips item reads on repeat pulls, and **`tracks_pulled_snapshot_id`** — docs/specs/partial-pulls-J.md §2.1, the `snapshot_id` in effect when that playlist's item read last *succeeded*. `snapshot_id` itself is refreshed for every playlist on every run whether or not the items are read, so it cannot mean "the stored items are current"; this column is the only one that does, and it is what makes an aborted pull resumable instead of silently poisoning the next refresh). `api_request` (docs/specs/partial-pulls-J.md §4.2) is the request log `api_log.py` writes, kept forever and never pruned. `artist_alias` / `reviewed_artist_pair` resolve Spotify's duplicate artist ids. `play` is the imported streaming history with `play_import` as its per-run log — a play resolves to a track through the **`played_uri_track`** view (no FK, no stored "foreign" flag), which unions `track.uri` with `track_uri_alias` so relinked uris resolve too; `track_uri_alias` maps a requested uri onto the track Spotify substituted for it, `roundtrip_failed_uri` remembers what couldn't be resolved, and `roundtrip_run` is the round-trip's per-run log. `VIEWS` is dropped and recreated whenever its definition changes — `_ensure_views` compares a hash of it against `meta.views_hash`, so an edit always takes effect while an ordinary restart needs no write lock (a rebuild can't take one while a pull is mid-transaction). It holds the artist read path: `resolved_track_artist` / `resolved_album_artist` (alias-resolved), `track_artist_credit`, `track_artist_role` (primary vs featured), and `track_artists` (the rendered display string) — **`track.artists` is write-only, never read**. `generation` (docs/specs/generations-B.md) is one row per current-favs playlist, `ordinal` **stored**, not derived from sort order; `snapshot.generation_declined` mutes the new-generation prompt for a playlist Finn said no to; `generation_presence` (DISTINCT-joined against `membership`/`track_group`) is what `generations.py` derives tenure from at query time. `wanted_uri` (docs/specs/entity-pages-K.md §6, docs/specs/grouping-fixes-backfill-M.md §4.3) is the queue of album-tracklist uris with no `track` row, merged into the round-trip's existing work list rather than being a second queue — `source` is `'album'` (queued by browsing an album page) or `'backfill'` (queued by the backfill job), and `album_id` is what lets M's settled/missing arithmetic be plain SQL instead of a per-page scan of every `tracklist_json`; inserts stay `INSERT OR IGNORE`, so **whichever route queues a uri first owns its `source`**. `set_meta` / `get_meta` are the `meta` key/value accessors (promoted out of `snapshot.py` when M's `roundtrip_listening_muted` flag needed a second caller) — they index by column name, so they need the `sqlite3.Row` factory `get_db()` / `connect()` set and `init_db()` deliberately does not, which is why `_ensure_views` still reads `views_hash` with its own tuple-indexed query; `album.tracklist_json` / `tracklist_pulled_at` and `artist.image_url` / `detail_pulled_at` cache the entity pages' one-request-per-first-view detail fetches — kept **out of `raw_json`**, which a snapshot pull overwrites with the simplified object embedded in every track. `score` (docs/specs/scoring-H.md) holds the materialized version/recording/release/track scores and **only** those four tiers — `group_id` is TEXT for all of them (a `track_id` verbatim at track tier, `str(canonical_group.id)` at the other three), and both columns are display-space numbers; it is wholesale-replaced by `scoring.recompute()`, never upserted, since a merge leaves dead group ids an upsert would strand forever.
- `snapshot.py` — the library snapshot engine: pulls playlists and their contents from Spotify into the append-only `membership` log and the normalized `track`/`album`/`artist` tables. Full-pull / refresh / backfill entry points, a background thread + module-global status dict, and a request counter. **Read-only w.r.t. Spotify — nothing here ever writes to the library.** It also owns the **shared track-ingest path** (`_usable_track` / `_parse_track_item` / `_upsert_track_full`): `roundtrip.py` calls the same three rather than growing a second way to write a track, so changing their signatures breaks it. **Partial/resumable pulls** (`docs/specs/partial-pulls-J.md`) are entirely *derived*, with no cursor and nothing checkpointed: `_is_stale` is the refresh rule and `_is_full_pull_target` the forced one, compared in **Python, not SQL**, because `NULL != NULL` is `NULL` and both columns are nullable. There is no Resume button — Refresh and Full pull *are* the resume. A forced pull additionally needs `meta.pull_force_epoch` to express "done *for this pull*", since its whole point is re-reading playlists whose `snapshot_id` has not changed; `_resolve_force_epoch` resumes that epoch while unfinished targets remain and **discounts playlists that are failing**, or one permanently broken playlist would pin the epoch forever and silently downgrade Full pull into "retry just that one". `_order_targets` materializes the order **once** per run (never-captured first, then `all_time` score descending), so nothing can reorder mid-run. **A playlist is the atom of resumption** — `_diff_playlist_tracks` reconciles against the *complete* item list, so a partially-fetched playlist would present as a mass removal; intra-playlist resume is out of scope permanently. `_pull_liked_songs` **commits its snapshot row before the item read**, exactly as `_sync_playlists_and_get_targets` does for every real playlist: Liked Songs is the one place those diverged, and holding that write open across the fetch made every `api_log` write wait out the full 30s busy timeout and vanish.
- `history_import.py` — play-history ingestion: extracts a Spotify GDPR streaming-history export zip into `data/streaming_history/<timestamp>/` and parses its JSON into `play`, deduped by a SHA-1 `row_hash` over 16 named source keys. Also owns the coverage counts the page reads, on the two bases step D split apart: **known to Symr** (a `track` row exists) vs **in your library** (that track also has a `membership` row). No Spotify API requests anywhere in it.
- `roundtrip.py` — **the only module that writes to the Spotify library.** Resolves played-but-unknown uris into real `track` rows by **replacing** the private `<Play History Loader>` scratch playlist's contents with 100 uris at a time and reading the full track objects back out of the playlist-items endpoint. Two invariants are load-bearing and were both learned the hard way: **replace, never append** (so the read is always `offset=0` and no running offset can drift), and **read the page as a bag, never as a sequence** — a track identifies itself by its own id, and a substituted one carries `linked_from` naming what was requested, so `track_uri_alias` is written *only* from `linked_from`, never inferred from position. Every run starts with a guard (name + owner verified live, zero writes if either is wrong); a 400'd batch is narrowed with the off-quota `open.spotify.com` probe, uris that don't come back are found by set difference, three consecutive failed batches trip a breaker, and each batch commits before the next begins. A **reconciliation pass** then retries what didn't come back — Spotify substitutes some ids without setting `linked_from`, and that pairing is auto-aliased only when the normalized full title *and* the album artist both match what the export recorded; anything less is flagged `needs a manual alias` rather than guessed (`roundtrip_failed_uri.reason` decides what is worth re-requesting: a probe-confirmed 404 never is). Those leftovers get a plain pick-a-track table on the page, whose candidates match on the normalized title *base* only — looser than the automatic rule on purpose, since that is what a human is there to judge. Writes no `membership` rows and runs no detection. The loader playlist id is a hardcoded constant with a `TODO` until the next full pull makes it pickable. `_WORK_LIST_SQL` has a second `UNION ALL` arm for `wanted_uri` (album-tracklist uris, `plays=0` so they sort after every played one); **"done" stays derived** — a wanted uri is finished when it resolves through `played_uri_track`, exactly like a played one, so nothing is checkpointed and nothing goes stale. `counts()` reports the queue as a **three-way partition** (docs/specs/grouping-fixes-backfill-M.md §4.6) — listening / album-page / album-backfill, arm 2 split by `source` — which sums to `remaining_uris` with no double-counting because arm 2 already excludes anything in `play`. The listening arm has no rows to delete, so `[Clear]` on it sets the `roundtrip_listening_muted` meta flag instead, **checked inside `_WORK_LIST_SQL` itself as a correlated subquery** so the constant stays one string with no Python branching; `_LISTENING_REMAINING_SQL` deliberately omits that filter, so a muted row still shows the count it *would* contribute rather than dropping to a meaningless zero.
- `backfill.py` (`docs/specs/grouping-fixes-backfill-M.md` §4) — the album backfill: the **fourth background job**, which fetches tracklists for albums Symr only partly owns in the most recent N generations and queues their unowned uris into `wanted_uri`. **It is an ingest route and nothing else** — no chaining into the round-trip or auto-group, no budget parameter, no scope beyond the two fixed buttons (N = 7 or 2), which *are* the budget control. Everything is **derived, never checkpointed**: an album is *settled* when `total_tracks - owned - unresolved-queued <= 0` and a generation is *handled* when all its albums are settled, so a partial run resumes by simply re-clicking, and clearing the queue is a free and complete undo that re-offers the same generations at **zero** requests (the tracklists are already stored). `work_list()` (the job) and `previews()` (the Add buttons' server-rendered counts) both go through `_derive()` on one shared `_settled_map()` / `_unhandled_ordinals_desc()` pass, so what the buttons promise and what the job does can't disagree. Unlike `entities.fetch_album_tracklist`'s deliberate one-request cap, its own fetch **pages past the first 50 items**; it commits per album and polls `jobs.stop_requested()` between them.
- `artists.py` — artist identity: per-track alias-resolved id sets for detection (`artist_sets`), plus duplicate-candidate detection and the merge/unmerge curation writes. Owns `artist_alias` / `reviewed_artist_pair` only.
- `canonical.py` — the four-tier (`release` → `recording` → `version` → `song`) canonical-grouping engine, plus the viewer read paths (`song_group_rows` **+ `hydrate_song_groups`** — deliberately two calls, so the caller ranks *all* groups cheaply and only builds a representative `track_display` for the capped slice it renders; the ranking itself lives in `app.py`, not here, because it needs `scoring.py`, which imports this module for `ensure_track_groups()`; `representative`, `tier_counts`, and the tier-agnostic `subtree` / `group_tree`, of which `nested_tree` / `song_tree` are now thin song-tier wrappers). `artist_credits_for_tracks` is the batched `{track_id: [{artist_id, name}]}` lookup every page linking individual artist names uses — `track_artists` / `track_display`'s `artists` is a pre-joined display string with no id to link to. Owns `canonical_group` / `track_group` / `reviewed_pair` and never touches `track` or `membership`. **`mark_reviewed_pairs(conn, pairs)` is the pair-level writer** and `mark_reviewed(conn, track_ids)` is a thin every-pair wrapper over it — a caller that means something narrower than "every pair in this bucket" must use the former, which is the whole of M1's fix (see `canonical_detect.cross_component_pairs`). `apply_partition` takes a **`cleanup` keyword**: `False` skips the four `_cleanup_tier` passes, which are a full `canonical_group × track_group` join each and dominate the cost of a batch — only a caller that runs `cleanup_all_tiers()` itself afterwards may pass it. **None of its functions commit — callers own the transaction.**
- **`/dev/canonical`'s page budget** — that page took 1.18s and 4.3MB of HTML; it now paints in ~112ms. Three separate fixes, and the order they were found in is the lesson: cap the listings (HTML volume), *then* stop hydrating rows that won't render (`song_group_rows` + `hydrate_song_groups`), *then* defer detection off the page load (`/api/canonical/cross/listing`). Capping alone bounded only `song_tree`×50, which was 5ms of 800ms. Anything added here should keep the rule: **work proportional to what's rendered, not to the library.** Detection's `_fetch_tracks` (~350ms — the big `GROUP BY`, `artist_sets`, `normalize_title` per track) is the remaining floor and is why the cross pane is async at all. Step H bought it back up to ~160–280ms, knowingly: **ranking has to see every group before the cap, or the cap returns the alphabetically-first 50 rather than the best 50**, so `song_scores()` over all ~8.8k song groups is the one thing here allowed to scale with the library. It stays cheap because it is one read of the materialized version tier plus a Python `combine()` per group — hydration still touches only the capped slice, which is the expensive half.
- `canonical_detect.py` — detection for that engine: proposes candidate groups and pre-filled tier labels from normalized titles, suffix classification (`base`/`version`/`recording`/`neutral`, keywords matched as whole token sequences against `normalize_suffix`), and a duration tolerance. **`cross_component_pairs`** is what `/api/canonical/cross/apply` marks reviewed — exactly the pairs `_cross_component_reviewed` checks, so it both settles the bucket and leaves every within-component (same-artist) pair for the main queue, where marking it would have suppressed it forever (docs/specs/grouping-fixes-backfill-M.md §1); it shares `_group_by_rule` with `_bucket_components` rather than re-implementing the union-find, because if the two ever disagreed about what a component is a bucket could resurface forever, and it reads `artists.artist_sets` directly to stay off `_fetch_tracks`'s ~350ms whole-library path. Also builds the cross-artist queue's buckets, filters them for the `/dev/canonical` listing (`filter_groups`, which honours SQL LIKE's `%` so it behaves like the LIKE-backed Groups filter beside it), and decides the deterministic auto-group rule. Reads `pending_tier_review` (the cross-artist assignments owing a version/recording/release pass, written by `/api/canonical/cross/apply`, keyed on track id because group ids get reconciled away) — **`pending_song_ids` owns the "group still has ≥2 members" filter**, so the count on `/dev/canonical` and the items `?queue=pending` serves can't disagree. Every candidate-group listing — main queue, cross-artist buckets, ad-hoc — ranks through the single `_order()` helper on `scoring.group_score` over its tracks' materialized scores; **`impact` is retired** and there is no second inline sort to drift out of step with it. Decides nothing and writes nothing — pure computation over `track`/`membership`, no Spotify calls.
- `canonical_autogroup.py` — the write side of that auto-group rule: closes every qualifying queue item in one batch of `apply_partition(cleanup=False)` calls, logs the run in `auto_group_run`, and takes a whole-table snapshot of `track_group`/`canonical_group`/`reviewed_pair` beforehand so undo is a wholesale restore. One level deep — a new run replaces the snapshot. Unlike `canonical.py`, these functions **do** commit.
- `grouping.py` — the org canvas's proximity/chained card grouping (`group_cards`) and the export-text renderer (`render_export_text`) behind `/api/export`. Pure geometry over card/label coordinates; no DB, no Spotify.
- `generations.py` (`docs/specs/generations-B.md`) — generations and **tenure**, deliberately distinct from membership: `generations()` / `tenures()` derive everything at query time from `generation_presence` (nothing materialized), take a `tier="version"|"song"` parameter (a whitelisted column lookup, never interpolated), and both read-only, never commit. `pending_new_generation()` / `confirm_generation()` / `decline_generation()` own the confirm-on-pull flow for new `vXX.Y.Z` playlists; callers commit those. `presence_for_tracks()` gives the ordinals a track set was present in (the strip every entity page renders) and `runs()` is the public run-collapsing helper `tenures()` uses internally. Read-only over `track`/`membership`/the canonical tables and makes no Spotify calls.
- `scoring.py` (`docs/specs/scoring-H.md`) — the one score, on one absolute scale. The **version group is the atom**: `recompute()` rolls weighted plays / rate over exposure / live memberships / tenure up to each version, saturates and weights them, shrinks toward a bucket baseline built from median *inputs* (never from any output score, so nothing is circular), and materializes both horizons — `all_time` and a 90-day `recent`, the same computation over a different window — into the `score` table, along with recording/release/track's own lightly-blended variants. Song, album, artist, playlist and any ad-hoc bag of tracks are **never materialized**: they aggregate at query time through `combine()`, the one weighted power mean every collection type shares — **the combiner does not know what it is combining**, so there are no artist- or album-specific terms. Stored values are **display-space** (the 10–99-ish number), so "score" means that everywhere outside this module; `combine()` runs in normalized space and callers `_undisplay()` first. Every parameter is a module constant with a warning, **not** in `config.py` and not environment-tunable — a per-environment parameter would silently leave the table scored under two algorithms. Recompute is always whole-library and wholesale-replacing (~1.8s), called at the end of every write path that touches an input. **Whether it blocks the request is decided by one rule** (`docs/specs/async-recompute-N.md` §4.1): **async where you are working a queue, synchronous where you clicked once and are waiting for the outcome anyway** — so the two canonical-apply endpoints, `/api/canonical/pin` and `artists.py`'s mark-same/unmerge call `request_recompute()`, while `/api/scoring/recompute`, `/dev/generations/confirm`, auto-group run/undo and all eleven job call sites still call `recompute()` inline. Async goes through **one coalescing worker thread** (`request_recompute()` / `_worker()`) — deliberately *not* `jobs.py`, because every job calls `recompute()` **while holding the slot** and would deadlock against its own closing call. Commits landing mid-pass set one flag and are absorbed by one extra pass, so holding Enter through ten items costs two or three recomputes; the worker **defers to any running job** and drops the flag, which is safe only because `ensure_fresh()` re-catches it. **`_worker_alive` is cleared in a single outer `finally`** — a stuck flag is this module's one unrecoverable state (nothing would ever spawn again, the backstop would defer forever, and no banner would appear, because `recompute()` never ran to record an error). Order at every async site is load-bearing: **commit first, then request** — the worker reads through its own connection. `ensure_fresh()` is the read backstop for paths that aren't jobs (`canonical.ensure_track_groups()` writes on a plain GET); it **enqueues, never recomputes inline**, owns a **dedicated module-level connection** for its `PRAGMA data_version` check — the pragma is only meaningful relative to one connection, so a per-request one would compare unrelated numbers — and **defers rather than checks while `jobs.active()` or the worker is alive**, remembering nothing while it does, so a job that dies without recomputing is still caught by the next request. `_failed_fingerprint` stops a *repeatable* failure spinning: the exact fingerprint that just failed is never auto-retried, any success clears it, and the manual button always retries. Read-only w.r.t. Spotify.
- `entities.py` (`docs/specs/entity-pages-K.md`) — the entity pages' read paths that belong to no existing owner: `play_stats` (total / past 30d / past 7d over a track set, resolved through **`played_uri_track`** so relinked uris count; a window whose start predates `MAX(play.ts)` returns `None`, which renders `—` rather than a lying `0`) and `playlists_for_tracks`. Also the two guarded detail fetches — `fetch_album_tracklist` / `fetch_artist_image` — which spend **at most one Spotify request, on that entity's own page, on first view only**, swallow every failure so the page still renders from the DB, and never page past the first 50 tracklist items. Fetching and queuing are **two functions, not one** (M §4.4): `queue_wanted_uris(conn, album_id, source)` runs off the *stored* `tracklist_json` at **zero** Spotify cost, so the album page calls it on **every** view while the guarded fetch still runs only on the first — that is what makes clearing a queue a real undo instead of a trap, since a cleared uri comes back the moment the page is revisited. The backfill job calls the same two, with `source='backfill'`, rather than growing a second way to write a `wanted_uri` row. Queues unowned uris rather than writing partial `track` rows. Read-only w.r.t. the Spotify library.

## Keep It Simple
- KISS. The goal is code that is **done, understandable, and works** — not production-grade or clever. AI tends to overdo complexity; don't. Reach for the simplest thing that fully solves the problem.
- **Security is the one exception to KISS — never do the bare minimum here.** Everything security-related must be done *fully and properly*, not just "right": secure coding practice (never leak tokens/secrets) **and** the implementation of things like login, auth, and session handling. Do those thoroughly.
- The other hard requirement: never corrupt or wrongly modify my real Spotify library. Beyond security and that, favor simplicity over robustness — the rest just needs to be done right.

## No Assumptions & the Stop-and-Ask Rule
- Never assume behavior, versions, libraries, or intent I haven't stated. If something is undefined, ask.
- **Stop-and-ask (token reduction):** the moment you're unsure or catch yourself weighing alternatives, stop right there and ask — do not keep reasoning through the options first. Ask immediately, get my answer, then continue the train of thought.
- **One try, then ask.** If an approach doesn't work on the first attempt, stop and ask for direction. Do not try a second approach, and never layer hacky fixes (overrides, workarounds) to force something through. Surface the problem instead of digging deeper.
- Prefer asking me over reading large, token-expensive docs. Only open those if I point you to them or say broader context is needed.

## When Asking Questions
- Always **number** questions (use sub-letters when nesting, e.g. 1, 2a, 2b) so I can reply item-by-item. This applies to any list I'll respond to point-by-point; plain prose replies don't need identifiers.
- **Brief first, then ballot.** Findings, reasoning and recommendations go in prose *above* the numbered list; each numbered item is the decision itself, ideally one line. A question carrying its own justification inline is hard to scan and hard to answer item-by-item — the identical list, re-asked with the rationale lifted out, reads far more clearly.
- **Compressing a question moves its "why" up, never deletes it.** If a fact matters enough to state, it stays on the page — just above the list rather than inside it. This is a rule about placement, not about asking less: never drop a real consideration to make a list look tidy.

## Git Workflow
Solo repo, single checkout at `/Users/finne/Projects/Spotify-Manager` (no worktrees). Branch prefixes: **`feat/`** features, **`chore/`** tooling/docs, **`fix/`** fixes. A feature branch carries both the spec (its first commit) and the implementation commits stacked on top.

These are **always-on tripwires** — warn *before* acting, then do whatever I decide. Never silently proceed past one; never refuse once I've answered.
1. **No committing to `main`.** Before any commit, check `git branch --show-current`; if it's `main` and this isn't a tiny main-level fix, stop and flag it — the work belongs on a branch.
2. **Confirm the branch before new work.** A fresh session inherits whatever branch was last checked out, which is likely wrong for new work. Confirming the branch is the *first* action of any new phase, before reading code: check `git branch --show-current`, propose a fresh branch off up-to-date `main` (or a switch to the right existing one), wait for my OK, then dive in.
3. **No premature merge/push.** Merging a branch into `main` and pushing happen only in the Verify finish-up — never during Plan or Implement.

Commits: commit only when I ask, in logical units — one for the spec, a few for implementation as needed, optionally one or more from verify. **Logical units are decided at the file level, never by splitting a single file's hunks across commits** — commit whole files together (`git add <file>`, not `git add -p`). A normal plan/implement/verify session's diff is one coherent piece of work even when a "logical" grouping would put different hunks of the same file in different commits; splitting hunks costs time, tokens, and is an easy way to stage the wrong thing. The one exception is a real mistake — edits for a genuinely separate concern that shouldn't have landed in this session/branch at all — where untangling by hunk is the correct fix, not a workflow shortcut. Commit in my name only — no Claude/AI co-author or attribution line. **Don't push without being asked.** The sanctioned merge+push is the Verify finish-up: a **`git merge --ff-only`** into `main` (keeps history linear, no merge-commit clutter) then push. This repo is solo and single-copy, so `--force-with-lease` is safe when a rewrite is the agreed fix.
