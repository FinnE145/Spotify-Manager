## Overview
**Symr** (**S**potif**Y** **M**anage**R**, pronounced "simmer") — a web-based music library manager.

A Flask app for maintaining and verifying a Spotify library that follows a specific set of personal conventions (an append-only "Finn All" master playlist, semver-named "current favs" playlists, an ATG playlist, and a CI/CL intake playlist). The full library/usage spec lives in `docs/library_spec.md` (TBD).

## Tech Stack
- **Python 3.14.5** (fall back to 3.12 if something doesn't work), **Flask**.
- **Spotipy** for Spotify Web API access — handles OAuth, token refresh, and paging.
- **SQLite** via the stdlib `sqlite3` + a thin helper (no ORM unless the schema forces it): library snapshot, version history, folder-structure record, cover library, canvas boards, etc.
- **Frontend:** server-rendered **Jinja templates + vanilla JS**, no SPA framework. Richer interactive JS only where a feature needs it (e.g. the org canvas) — settle those specifics in that feature's spec.
- **Env:** `venv` + `requirements.txt`.
- v1 is read-only. Fill in remaining choices (charts, etc.) as features are specced. Never assume an unstated version or library.

Routes themselves stay (no blueprints, `P3_refactor.md` §2).
- `config.py` — every setting, read from the environment via `.env` (python-dotenv): Spotify credentials / redirect / scopes, `DB_PATH` (`SYMR_DB_PATH`), the spotipy token-cache path, `APP_PORT` / `APP_DEBUG`, `MAX_CONTENT_LENGTH`, `SPOTIFY_CANONICAL_HOST` / `SPOTIFY_CANONICAL_ORIGIN` (parsed once at import off `SPOTIFY_REDIRECT_URI` for `/login`'s host redirect, T §1.2 — here rather than in `app.py` because a module constant is testable with no request context, and `.hostname` is what makes the comparison port-blind), and `SECRET_KEY` (read from `SYMR_SECRET_KEY` with **no fallback** since Q §5.1 — a random per-process key silently invalidated every session on each restart, which breaks login on a service that restarts on its own). Credentials live in the environment only — never hard-code or log them.
- `spotify_client.py` — the only place an authed Spotify client is built: `get_auth_manager()` (OAuth, scopes from config, on-disk token cache) and `get_spotify_client()` (returns `None` when there's no valid cached token). Its custom `requests` session sets `respect_retry_after_header=False` so a 429 raises immediately instead of blocking for an hours-long app-quota `Retry-After` — `snapshot.py`'s `_call()` handles the wait itself. Scopes are read-only. Both session builds instantiate `api_log.LoggingSession`, and deliberately **two separate instances**: sharing one would apply the API client's GET-only retry policy to `SpotifyOAuth`'s token-refresh POSTs, changing auth behaviour to get logging.
- `api_log.py` (`docs/specs/partial-pulls-J.md` §4) — the API request log. `LoggingSession` overrides `requests.Session.request()`, so **every** outbound Spotify request gets an `api_request` row regardless of caller, including the entity pages' detail fetches that never go through a job — hooking the session rather than `jobs.call` is what makes that true. `api_context` is a **contextvar, not a module global**: a job's background thread and a page-load thread run concurrently, and a global would let one overwrite the other's label. `record()` opens its own connection per write (no `check_same_thread`, no lock, ~1.5ms against a 100ms+ request) and **swallows every exception — a logging failure must never break the request it is logging**, which also means a lost row is silent, so no job may hold an open write transaction across a Spotify request (see `snapshot._pull_liked_songs`). Stores **no headers, no bodies, no response content** — only `Retry-After` by name into its own column and `len(response.content)` as an integer. `request_counts()` is the `/dev` row's two rolling counts, filtered to `host = 'api.spotify.com'` so token refreshes don't inflate the quota picture.
- `jobs.py` — the one background-job slot. A single module lock guards a single `_active` job name, so claiming the slot is one atomic check-and-set (`try_start`) with no lock ordering and no race — `snapshot.py` / `history_import.py` / `roundtrip.py` / `backfill.py` no longer own job locks of their own. Also owns cooperative stopping (`request_stop` / `stop_requested` — a flag the job polls at its own safe points, never a kill; all four jobs now poll it), sets `api_log.api_context` to the job name in `try_start`'s `run()` wrapper, `now_iso()`, the `RateLimited` fail-fast wrapper `call(status, fn, …)` that every Spotify request in every job goes through, and `JobStatus` (per-job progress fields + a capped 200-entry event log; `running` is *derived* from `jobs.active()`, never stored).
- `db.py` — SQLite `SCHEMA` + additive migrations (`_migrate`) + `VIEWS`. Library metadata is normalized: `track`, `album`, `artist`, plus `track_artist` / `album_artist` join tables carrying per-credit `position`; each of `track`/`album`/`artist` also keeps a verbatim `raw_json` of the Spotify object. `membership` is the append-only per-playlist log; `snapshot` is per-playlist state (including the `excluded` flag that skips item reads on repeat pulls, and **`tracks_pulled_snapshot_id`** — docs/specs/partial-pulls-J.md §2.1, the `snapshot_id` in effect when that playlist's item read last *succeeded*. `snapshot_id` itself is refreshed for every playlist on every run whether or not the items are read, so it cannot mean "the stored items are current"; this column is the only one that does, and it is what makes an aborted pull resumable instead of silently poisoning the next refresh). `api_request` (docs/specs/partial-pulls-J.md §4.2) is the request log `api_log.py` writes, kept forever and never pruned. `artist_alias` / `reviewed_artist_pair` resolve Spotify's duplicate artist ids. `scrobble_poll` (docs/specs/scrobbling-R.md §3.1) is the per-poll log `scrobble.py` writes — one row per poll, kept forever, and `play.poll_id` is its additive FK (NULL for every exported play, exactly as `import_id` is NULL for every scrobbled one); `track_isrc_absent` is the settled-exceptions table for tracks Spotify has no ISRC to give, shaped like `reviewed_pair` rather than `roundtrip_failed_uri` — a track that resolved perfectly, not a uri that failed to. `play` is the imported streaming history with `play_import` as its per-run log — a play resolves to a track through the **`played_uri_track`** view (no FK, no stored "foreign" flag), which unions `track.uri` with `track_uri_alias` so relinked uris resolve too; `track_uri_alias` maps a requested uri onto the track Spotify substituted for it, `roundtrip_failed_uri` remembers what couldn't be resolved, and `roundtrip_run` is the round-trip's per-run log. `VIEWS` is dropped and recreated whenever its definition changes — `_ensure_views` compares a hash of it against `meta.views_hash`, so an edit always takes effect while an ordinary restart needs no write lock (a rebuild can't take one while a pull is mid-transaction). It holds the artist read path: `resolved_track_artist` / `resolved_album_artist` (alias-resolved), `track_artist_credit`, `track_artist_role` (primary vs featured), and `track_artists` (the rendered display string) — **`track.artists` is write-only, never read**. `generation` (docs/specs/generations-B.md) is one row per current-favs playlist, `ordinal` **stored**, not derived from sort order; `snapshot.generation_declined` mutes the new-generation prompt for a playlist Finn said no to; `generation_presence` (DISTINCT-joined against `membership`/`track_group`) is what `generations.py` derives tenure from at query time. `wanted_uri` (docs/specs/entity-pages-K.md §6, docs/specs/grouping-fixes-backfill-M.md §4.3) is the queue of album-tracklist uris with no `track` row, merged into the round-trip's existing work list rather than being a second queue — `source` is `'album'` (queued by browsing an album page) or `'backfill'` (queued by the backfill job), and `album_id` is what lets M's settled/missing arithmetic be plain SQL instead of a per-page scan of every `tracklist_json`; inserts stay `INSERT OR IGNORE`, so **whichever route queues a uri first owns its `source`**. `set_meta` / `get_meta` are the `meta` key/value accessors (promoted out of `snapshot.py` when M's `roundtrip_listening_muted` flag needed a second caller) — they index by column name, so they need the `sqlite3.Row` factory `get_db()` / `connect()` set and `init_db()` deliberately does not, which is why `_ensure_views` still reads `views_hash` with its own tuple-indexed query; `album.tracklist_json` / `tracklist_pulled_at` and `artist.image_url` / `detail_pulled_at` cache the entity pages' one-request-per-first-view detail fetches — kept **out of `raw_json`**, which a snapshot pull overwrites with the simplified object embedded in every track. `score` (docs/specs/scoring-H.md) holds the materialized version/recording/release/track scores and **only** those four tiers — `group_id` is TEXT for all of them (a `track_id` verbatim at track tier, `str(canonical_group.id)` at the other three), and both columns are display-space numbers; it is wholesale-replaced by `scoring.recompute()`, never upserted, since a merge leaves dead group ids an upsert would strand forever.
- `snapshot.py` — the library snapshot engine: pulls playlists and their contents from Spotify into the append-only `membership` log and the normalized `track`/`album`/`artist` tables. Full-pull / refresh / backfill entry points, a background thread + module-global status dict, and a request counter. **Read-only w.r.t. Spotify — nothing here ever writes to the library.** It also owns the **shared track-ingest path** (`_usable_track` / `_parse_track_item` / `_upsert_track_full`): `roundtrip.py` calls the same three rather than growing a second way to write a track, so changing their signatures breaks it. **Partial/resumable pulls** (`docs/specs/partial-pulls-J.md`) are entirely *derived*, with no cursor and nothing checkpointed: `_is_stale` is the refresh rule and `_is_full_pull_target` the forced one, compared in **Python, not SQL**, because `NULL != NULL` is `NULL` and both columns are nullable. There is no Resume button — Refresh and Full pull *are* the resume. A forced pull additionally needs `meta.pull_force_epoch` to express "done *for this pull*", since its whole point is re-reading playlists whose `snapshot_id` has not changed; `_resolve_force_epoch` resumes that epoch while unfinished targets remain and **discounts playlists that are failing**, or one permanently broken playlist would pin the epoch forever and silently downgrade Full pull into "retry just that one". `_order_targets` materializes the order **once** per run (never-captured first, then `all_time` score descending), so nothing can reorder mid-run. **A playlist is the atom of resumption** — `_diff_playlist_tracks` reconciles against the *complete* item list, so a partially-fetched playlist would present as a mass removal; intra-playlist resume is out of scope permanently. `_pull_liked_songs` **commits its snapshot row before the item read**, exactly as `_sync_playlists_and_get_targets` does for every real playlist: Liked Songs is the one place those diverged, and holding that write open across the fetch made every `api_log` write wait out the full 30s busy timeout and vanish. `index_data(conn, q)` (P3 session 3) is `/dev/snapshot`'s whole read path, returning exactly the template's kwargs — **except** its pending-generation prompt, which stays in the route: it belongs to `generations.py`, and fetching it here would give this module its first dependency on that one, for a value it does not otherwise care about.
- `history_import.py` — play-history ingestion: extracts a Spotify GDPR streaming-history export zip into `data/streaming_history/<timestamp>/` and parses its JSON into `play`, deduped by a SHA-1 `row_hash` over 16 named source keys. Also owns the coverage counts the page reads, on the two bases step D split apart: **known to Symr** (a `track` row exists) vs **in your library** (that track also has a `membership` row). On a *successful* import it also deletes every `source = 'scrobble'` play its `range_end` covers (docs/specs/scrobbling-R.md §6) — a scrobble is a low-fidelity placeholder the export replaces, never merged or flagged. No Spotify API requests anywhere in it.
- `roundtrip.py` — **the only module that writes to the Spotify library.** Resolves played-but-unknown uris into real `track` rows by **replacing** the private `<Play History Loader>` scratch playlist's contents with 100 uris at a time and reading the full track objects back out of the playlist-items endpoint. Two invariants are load-bearing and were both learned the hard way: **replace, never append** (so the read is always `offset=0` and no running offset can drift), and **read the page as a bag, never as a sequence** — a track identifies itself by its own id, and a substituted one carries `linked_from` naming what was requested, so `track_uri_alias` is written *only* from `linked_from`, never inferred from position. Every run starts with a guard (name + owner verified live, zero writes if either is wrong); a 400'd batch is narrowed with the off-quota `open.spotify.com` probe, uris that don't come back are found by set difference, three consecutive failed batches trip a breaker, and each batch commits before the next begins. A **reconciliation pass** then retries what didn't come back — Spotify substitutes some ids without setting `linked_from`, and that pairing is auto-aliased only when the normalized full title *and* the album artist both match what the export recorded; anything less is flagged `needs a manual alias` rather than guessed (`roundtrip_failed_uri.reason` decides what is worth re-requesting: a probe-confirmed 404 never is). Those leftovers get a plain pick-a-track table on the page, whose candidates match on the normalized title *base* only — looser than the automatic rule on purpose, since that is what a human is there to judge. Writes no `membership` rows and runs no detection. The loader playlist id is a hardcoded constant with a `TODO` until the next full pull makes it pickable. `_WORK_LIST_SQL` has a second `UNION ALL` arm for `wanted_uri` (album-tracklist uris, `plays=0` so they sort after every played one); **"done" stays derived** — a wanted uri is finished when it resolves through `played_uri_track`, exactly like a played one, so nothing is checkpointed and nothing goes stale. A **third arm** (docs/specs/scrobbling-R.md §5.2) covers tracks that resolved but carry no `isrc` — what a scrobble ingest leaves behind, since recently-played omits `external_ids` entirely; `isrc IS NULL` **is** the marker, so no flag is introduced, and `track_isrc_absent` is that arm's own stop condition, written by `_load_and_read` whenever a returned full object *still* leaves the stored `isrc` NULL. It is deliberately a separate arm, not a widening of the listening arm, whose mute flag would otherwise silently mute this too. **`requests_estimate(n_uris)`** (`2 * ceil(n / 100) + 3`) is module-level and is the *single* home for that formula: `backfill.previews()` calls it too, so an Add button's projected round-trip cost cannot drift from the Status panel's own figure (T §2.3). `counts()` reports the queue as a **four-way partition** (docs/specs/grouping-fixes-backfill-M.md §4.6, extended by R §5.3) — listening / album-page / album-backfill / incomplete-ISRC, arm 2 split by `source` — which sums to `remaining_uris` with no double-counting because arm 2 already excludes anything in `play` and arm 3 is disjoint from arm 1 by construction (that one is `x.track_id IS NULL`, this one is resolved-but-incomplete). `[Clear]` on the ISRC row is `settle_incomplete_isrc`, which **settles rather than deletes** — there is nothing to re-add, so it `INSERT OR IGNORE`s the currently-matching track ids into `track_isrc_absent`. The listening arm has no rows to delete, so `[Clear]` on it sets the `roundtrip_listening_muted` meta flag instead, **checked inside `_WORK_LIST_SQL` itself as a correlated subquery** so the constant stays one string with no Python branching; `_LISTENING_REMAINING_SQL` deliberately omits that filter, so a muted row still shows the count it *would* contribute rather than dropping to a meaningless zero.
- `backfill.py` (`docs/specs/grouping-fixes-backfill-M.md` §4) — the album backfill: the **fourth background job**, which fetches tracklists for albums Symr only partly owns in the most recent N generations and queues their unowned uris into `wanted_uri`. **It is an ingest route and nothing else** — no chaining into the round-trip or auto-group, no budget parameter, no scope beyond the two fixed buttons (N = 7 or 2), which *are* the budget control. Everything is **derived, never checkpointed**: an album is *settled* when `total_tracks - owned - unresolved-queued <= 0` and a generation is *handled* when all its albums are settled, so a partial run resumes by simply re-clicking, and clearing the queue is a free and complete undo that re-offers the same generations at **zero** requests (the tracklists are already stored). `work_list()` (the job) and `previews()` (the Add buttons' server-rendered counts) both go through `_derive()` on one shared `_settled_map()` / `_unhandled_ordinals_desc()` pass, so what the buttons promise and what the job does can't disagree. **`_settled_map` returns the raw `missing` count, not a boolean** — every caller derives `missing <= 0` itself — because that number *is* how many uris an Add would queue, which `_derive` sums into `queued_uris` at zero further cost (T §2.2); `previews(conn, remaining_uris)` then takes the round-trip's own queue size and calls `roundtrip.requests_estimate` on the two combined. That `roundtrip` import is the module's one edge into it and adds no cycle (`roundtrip.py` cannot reach `backfill`); "no chaining into the round-trip" is still true and is now asserted **behaviourally** — a run starts no job — rather than by a static import check the shared formula would have broken. Unlike `entities.fetch_album_tracklist`'s deliberate one-request cap, its own fetch **pages past the first 50 items**; it commits per album and polls `jobs.stop_requested()` between them.
- `scrobble.py` (`docs/specs/scrobbling-R.md`) — scrobbling from `GET /v1/me/player/recently-played`, polled every 100 minutes (~14.4 requests/day). **Not a job** — a single request doesn't justify a `JobStatus`, so it never touches `jobs.py`'s slot; `poll(conn)` is the whole feature, called identically by the daemon loop and by `/dev/scrobble`'s manual **Poll now** button, so the feature is fully exercisable on the laptop with the thread never running. `start()` is called **only from `serve.py`**, never `app.py`'s `app.run()` — what makes scrobbling production-only by construction. Ingests through the same `snapshot._usable_track` / `_parse_track_item` / `_upsert_track_full` path every other ingest route uses, so a scrobbled track has a name/album/artists immediately, but a NULL `isrc` — the endpoint's track object omits `external_ids` entirely — which is why `roundtrip.py` gains a third work-list arm to fill it in later, with `track_isrc_absent` as that arm's own settled-exceptions stop condition (mirroring `reviewed_pair`, not `roundtrip_failed_uri` — the opposite case, a uri that failed to resolve). Writes `play` rows with `source = 'scrobble'` and a `poll_id` FK into `scrobble_poll`, its own kept-forever per-poll log (one row per poll, including a poll that inserts nothing — the only liveness signal `/dev/scrobble` has); `ms_played` is derived from the gap to the next-older item in the batch (`min(gap, duration_ms)`, falling back to a DB lookup for the batch's oldest item), since the endpoint reports no `ms_played` of its own. `history_import._finish` deletes every `source = 'scrobble'` row a *successful* import's range covers, before that import's own commit — a scrobble is explicitly non-authoritative, a low-fidelity placeholder the export replaces, never merged or flagged. **That delete is necessary but not sufficient, and the pairing is load-bearing** (§6.1, found in verification): deleting a row destroys the `row_hash` `INSERT OR IGNORE` dedupes against, and the 50-deep window keeps serving the same items for days, so `_ingest` *also* skips any item at or before `MAX(ts) FROM play WHERE source = 'export'` — without it every superseded play returned within one interval, measured at 26 double-counted plays on the real library. A 429 sets `scrobble_backoff_until` (a `meta` key, checked before every request) rather than blocking the thread; `scrobble_enabled = '0'` pauses it the same way. **`_loop` catches around the whole of `poll()`, not just the request** — nothing restarts the thread, so one `database is locked` from the commit would otherwise end scrobbling for the life of the container, silently; the failure is recorded by `_record_loop_error` on a *fresh* connection, which swallows its own failures. **`_next_wake_at` is in-process module state** (like `jobs._active`, and readable from a request thread only because Q §6.5 rules out a second worker process): the next poll is read off the thread, never derived from the last `scrobble_poll` row, because a manual **Poll now** writes a row without touching the sleep — and `None` means no poller in this process, which `/dev/scrobble` says outright instead of inventing a time. `index_data(conn)` is `/dev/scrobble`'s whole read path, and is what **both** `/api/scrobble/poll` and `/api/scrobble/toggle` return.
- `artists.py` — artist identity: per-track alias-resolved id sets for detection (`artist_sets`), plus duplicate-candidate detection and the merge/unmerge curation writes. Owns `artist_alias` / `reviewed_artist_pair` only.
- `canonical.py` — the four-tier (`release` → `recording` → `version` → `song`) canonical-grouping engine, plus the viewer read paths (`song_group_rows` **+ `hydrate_song_groups`** — deliberately two calls, so the caller ranks *all* groups cheaply and only builds a representative `track_display` for the capped slice it renders; the ranking itself lives in `app.py`, not here, because it needs `scoring.py`, which imports this module for `ensure_track_groups()`; `representative`, `tier_counts`, and the tier-agnostic `subtree` / `group_tree`, of which `nested_tree` / `song_tree` are now thin song-tier wrappers). `artist_credits_for_tracks` is the batched `{track_id: [{artist_id, name}]}` lookup every page linking individual artist names uses — `track_artists` / `track_display`'s `artists` is a pre-joined display string with no id to link to. Owns `canonical_group` / `track_group` / `reviewed_pair` and never touches `track` or `membership`. **`mark_reviewed_pairs(conn, pairs)` is the pair-level writer** and `mark_reviewed(conn, track_ids)` is a thin every-pair wrapper over it — a caller that means something narrower than "every pair in this bucket" must use the former, which is the whole of M1's fix (see `canonical_detect.cross_component_pairs`). `apply_partition` takes a **`cleanup` keyword**: `False` skips the four `_cleanup_tier` passes, which are a full `canonical_group × track_group` join each and dominate the cost of a batch — only a caller that runs `cleanup_all_tiers()` itself afterwards may pass it. **None of its functions commit — callers own the transaction.**
- **`/dev/canonical`'s page budget** — that page took 1.18s and 4.3MB of HTML; it now paints in ~112ms. Three separate fixes, and the order they were found in is the lesson: cap the listings (HTML volume), *then* stop hydrating rows that won't render (`song_group_rows` + `hydrate_song_groups`), *then* defer detection off the page load (`/api/canonical/cross/listing`). Capping alone bounded only `song_tree`×50, which was 5ms of 800ms. Anything added here should keep the rule: **work proportional to what's rendered, not to the library.** Detection's `_fetch_tracks` (~350ms — the big `GROUP BY`, `artist_sets`, `normalize_title` per track) is the remaining floor and is why the cross pane is async at all. Step H bought it back up to ~160–280ms, knowingly: **ranking has to see every group before the cap, or the cap returns the alphabetically-first 50 rather than the best 50**, so `song_scores()` over all ~10.2k song groups (2026-08-22) is the one thing here allowed to scale with the library. It stays cheap because it is one read of the materialized version tier plus a Python `combine()` per group — hydration still touches only the capped slice, which is the expensive half.

- `scoring.py` (`docs/specs/scoring-H.md`) — the one score, on one absolute scale. The **version group is the atom**: `recompute()` rolls weighted plays / rate over exposure / live memberships / tenure up to each version, saturates and weights them, shrinks toward a bucket baseline built from median *inputs* (never from any output score, so nothing is circular), and materializes both horizons — `all_time` and a 90-day `recent`, the same computation over a different window — into the `score` table, along with recording/release/track's own lightly-blended variants. Song, album, artist, playlist and any ad-hoc bag of tracks are **never materialized**: they aggregate at query time through `combine()`, the one weighted power mean every collection type shares — **the combiner does not know what it is combining**, so there are no artist- or album-specific terms. Stored values are **display-space** (the 10–99-ish number), so "score" means that everywhere outside this module; `combine()` runs in normalized space and callers `_undisplay()` first. Every parameter is a module constant with a warning, **not** in `config.py` and not environment-tunable — a per-environment parameter would silently leave the table scored under two algorithms. Recompute is always whole-library and wholesale-replacing (~1.8s), called at the end of every write path that touches an input. **Whether it blocks the request is decided by one rule** (`docs/specs/async-recompute-N.md` §4.1): **async where you are working a queue, synchronous where you clicked once and are waiting for the outcome anyway** — so the two canonical-apply endpoints, `/api/canonical/pin` and `artists.py`'s mark-same/unmerge call `request_recompute()`, while `/api/scoring/recompute`, `/dev/generations/confirm`, auto-group run/undo and all eleven job call sites still call `recompute()` inline. Async goes through **one coalescing worker thread** (`request_recompute()` / `_worker()`) — deliberately *not* `jobs.py`, because every job calls `recompute()` **while holding the slot** and would deadlock against its own closing call. Commits landing mid-pass set one flag and are absorbed by one extra pass, so holding Enter through ten items costs two or three recomputes; the worker **defers to any running job** and drops the flag, which is safe only because `ensure_fresh()` re-catches it. **`_worker_alive` is cleared in a single outer `finally`** — a stuck flag is this module's one unrecoverable state (nothing would ever spawn again, the backstop would defer forever, and no banner would appear, because `recompute()` never ran to record an error). Order at every async site is load-bearing: **commit first, then request** — the worker reads through its own connection. `ensure_fresh()` is the read backstop for paths that aren't jobs (`canonical.ensure_track_groups()` writes on a plain GET); it **enqueues, never recomputes inline**, owns a **dedicated module-level connection** for its `PRAGMA data_version` check — the pragma is only meaningful relative to one connection, so a per-request one would compare unrelated numbers — and **defers rather than checks while `jobs.active()` or the worker is alive**, remembering nothing while it does, so a job that dies without recomputing is still caught by the next request. `_failed_fingerprint` stops a *repeatable* failure spinning: the exact fingerprint that just failed is never auto-retried, any success clears it, and the manual button always retries. Read-only w.r.t. Spotify.

- `search.py` (`docs/specs/better-search-L.md`, **`docs/specs/better-search-L2.md`, which supersedes L's whole relevance formula — read L2 for how matching works today**) — **one matcher, used by three surfaces**: `/search`, the navbar dropdown (`/api/search`) and each type section's See more (`/api/search/more`) all slice the same lists `rank()` builds, so there is no separate "dropdown ranking" and "page ranking". A two-stage fuzzy matcher over `normalize.base_string`: a trigram prefilter (`_stage1_candidates`) narrows the ~18,461 distinct normalized names across `track`/`album`/`artist`/`snapshot` down to a handful, and only those get the token-aware `SequenceMatcher` blend — the design that makes typo tolerance affordable at all, since scoring every name costs 270–840ms against 4–44ms with the prefilter (L §10). The scoring universe is **cached in-process, staleness-checked on `PRAGMA data_version` against a dedicated module-level connection** — `scoring._checker()`'s exact shape, and for the same reason (the pragma is only meaningful relative to the connection that reads it). Stage 2 is **L2's**, and L's `own`/`assoc`/`BUMP` are gone: every `SequenceMatcher` ratio is **gated at `FUZZY_FLOOR` — below it, 0.0** (`_tsim`'s difflib branch *and* `_whole_string`, since gating one leaves the noise the other way in), because the ratio has a high noise floor on short strings ("test" vs "best" is 0.750; one substitution in a five-letter word is 0.800 whichever word it is, so no threshold and no edit rule separates a typo from a different word — the gate declines to guess, and `creap`→*creep* is the accepted loss). The equality and prefix branches are **not** gated; the prefix branch is what makes an as-you-type query work and is not a fuzzy match. A name then yields **one value per query token**, not one score (`_name_token_scores`, with `whole` folded into every token so a match can cross a boundary the query doesn't share), and `_relevance` is the **mean over query tokens of `max(own_i, ASSOC_WEIGHT * assoc_i)`** — a coverage measure, which is what lets `taylor swift cardigan` spread two tokens onto the artist and one onto the title instead of dropping the right answer. **§4.3 is a rule, not arithmetic**: an entity whose own name contributes nothing to *any* query token is dropped before relevance is computed, regardless of what its associated names score — L got that from `own` multiplying, but coverage has no such multiply and an artist-only match lands at exactly `RELEVANCE_FLOOR`, so stating it outright keeps the guarantee from depending on two unrelated constants being equal. `_rank_key = max(score, SCORE_FLOOR) * relevance ** ALPHA` keeps L's shape and both constants — `SCORE_FLOOR` is the fix for a hole otherwise silent: `scoring.scores_for_tier` returns nothing for an entity with no materialized row, and a plain multiply would rank a brand-new exact match at zero. Albums additionally **dedupe after ranking** (L2 §5) on name + credited artists + *intersecting* `track_group.release_id` sets — display-only, nothing written, and the release condition is what keeps a deluxe edition from swallowing the album it reissued (cover equality was measured and rejected: it collapses 0 of 294 groups, since Spotify gives every duplicate album id its own artwork URL). Songs rank at the **version tier**: candidates are individual tracks (own = the track's own title, never a credited artist's — the K §10 rule L replaces), but `_rank_songs` batches the version-group lookup in one query over every candidate track id and dedupes to one row per version group, keeping the highest-relevance member (ties broken by that member's own track-tier score). Artists dedupe onto their `artist_alias`-resolved canonical id, matching K's original convention (not named as replaced in L's §2 table). **Ranking sees every candidate before any cap** (§4.7) — `rank()` returns unclipped lists; only the hydration functions (`_hydrate_songs` / `_hydrate_albums` / `_hydrate_artists` / `_hydrate_playlists`, batched one query per type) touch anything past what will actually render, called with the already-capped slice by `search_page` / `search_dropdown` / `search_more`, the three functions `app.py`'s routes call directly. `_hydrate_combined` flattens all four to one uniform row shape (type label, link kind + id, name, `artists`, cover, score); **`artists` is absent for artist and playlist rows by design** — an artist row is its own artist — which is why `_search_combined.html` truth-tests it rather than giving it a column. Imports `normalize`, `canonical`, `scoring`, `db`; nothing imports it but `app.py` — no cycle, since `normalize` imports nothing project-level and `scoring` doesn't reach back here. Read-only w.r.t. both Spotify and the database; `/search`'s own route keeps the `canonical.ensure_track_groups(conn)` + commit pairing, since a GET returning a listing (the two async endpoints) has no business taking a write lock — and it gates that write on **`is_searchable(q)`, not on `q` being non-empty**, which is the one piece of the threshold that lives outside `rank()`: a sub-`MIN_QUERY_LEN` query returns nothing either way, so `?q=a` taking a write lock was pure cost (found at Verify).

## Keep It Simple
- KISS. The goal is code that is **done, understandable, and works** — not production-grade or clever. AI tends to overdo complexity; don't. Reach for the simplest thing that fully solves the problem.
- **Security is the one exception to KISS — never do the bare minimum here.** Everything security-related must be done *fully and properly*, not just "right": secure coding practice (never leak tokens/secrets) **and** the implementation of things like login, auth, and session handling. Do those thoroughly.
- The other hard requirement: never corrupt or wrongly modify my real Spotify library. Beyond security and that, favor simplicity over robustness — the rest just needs to be done right.

## Tests
The suite's whole value is whether a test can **fail**. A green test that a broken implementation would also satisfy was the most common defect step P found — in every session, without exception. Two questions, always: *of each test*, what would a wrong implementation have produced here? *Of each module*, what does it produce — a stored column, a returned key, a branch — that no test reads at all? The second is not a refinement of the first, and the first cannot reach it. **Mutation is the only instrument that finds either**; coverage is structurally blind to the second, since code producing an unread value executes exactly as if it were read. `symr-implement` carries the rules for writing them and `symr-verify` for checking them; `docs/codebase-health/P2_findings.md` and `P3_findings.md` are the worked examples, and `post_P_sweep.md` is the one measurement of how well the suite actually holds up — 372 mutants over the four highest-risk modules, three of them at 100%.

## No Assumptions & the Stop-and-Ask Rule
- Never assume behavior, versions, libraries, or intent I haven't stated. If something is undefined, ask.
- **Stop-and-ask (token reduction):** the moment you're unsure or catch yourself weighing alternatives, stop right there and ask — do not keep reasoning through the options first. Ask immediately, get my answer, then continue the train of thought.
- **One try, then ask.** If an approach doesn't work on the first attempt, stop and ask for direction. Do not try a second approach, and never layer hacky fixes (overrides, workarounds) to force something through. Surface the problem instead of digging deeper.
- Prefer asking me over reading large, token-expensive docs. Only open those if I point you to them or say broader context is needed.

## When Asking Questions
- Always **number** questions (use sub-letters when nesting, e.g. 1, 2a, 2b) so I can reply item-by-item. This applies to any list I'll respond to point-by-point; plain prose replies don't need identifiers.
- **Brief first, then ballot.** Findings, reasoning and recommendations go in prose *above* the numbered list; each numbered item is the decision itself, ideally one line. A question carrying its own justification inline is hard to scan and hard to answer item-by-item — the identical list, re-asked with the rationale lifted out, reads far more clearly.
- **Compressing a question moves its "why" up, never deletes it.** If a fact matters enough to state, it stays on the page — just above the list rather than inside it. This is a rule about placement, not about asking less: never drop a real consideration to make a list look tidy.

## Frontend

## Git Workflow
Solo repo, single checkout at `/Users/finne/Projects/Spotify-Manager` (no worktrees). Branch prefixes: **`feat/`** features, **`chore/`** tooling/docs, **`fix/`** fixes. A feature branch carries both the spec (its first commit) and the implementation commits stacked on top.

These are **always-on tripwires** — warn *before* acting, then do whatever I decide. Never silently proceed past one; never refuse once I've answered.
1. **No committing to `main`.** Before any commit, check `git branch --show-current`; if it's `main` and this isn't a tiny main-level fix, stop and flag it — the work belongs on a branch.
2. **Confirm the branch before new work.** A fresh session inherits whatever branch was last checked out, which is likely wrong for new work. Confirming the branch is the *first* action of any new phase, before reading code: check `git branch --show-current`, propose a fresh branch off up-to-date `main` (or a switch to the right existing one), wait for my OK, then dive in.
3. **No premature merge/push.** Merging a branch into `main` and pushing happen only in the Verify finish-up — never during Plan or Implement.

Commits: commit only when I ask, in logical units — one for the spec, a few for implementation as needed, optionally one or more from verify. **Logical units are decided at the file level, never by splitting a single file's hunks across commits** — commit whole files together (`git add <file>`, not `git add -p`). A normal plan/implement/verify session's diff is one coherent piece of work even when a "logical" grouping would put different hunks of the same file in different commits; splitting hunks costs time, tokens, and is an easy way to stage the wrong thing. The one exception is a real mistake — edits for a genuinely separate concern that shouldn't have landed in this session/branch at all — where untangling by hunk is the correct fix, not a workflow shortcut. Commit in my name only — no Claude/AI co-author or attribution line. **Don't push without being asked.** The sanctioned merge+push is the Verify finish-up: a **`git merge --ff-only`** into `main` (keeps history linear, no merge-commit clutter) then push. This repo is solo and single-copy, so `--force-with-lease` is safe when a rewrite is the agreed fix.
