## Overview
**Symr** (**S**potif**Y** **M**anage**R**, pronounced "simmer") — a web-based music library manager.

A Flask app for maintaining and verifying a Spotify library that follows a specific set of personal conventions (an append-only "Finn All" master playlist, semver-named "current favs" playlists, an ATG playlist, and a CI/CL intake playlist). The full library/usage spec lives in `docs/library_spec.md` (TBD).

## Tech Stack
- **Python 3.14.5** (fall back to 3.12 if something doesn't work), **Flask**.
- **Spotipy** for Spotify Web API access — handles OAuth, token refresh, and paging.
- **SQLite** via the stdlib `sqlite3` + a thin helper (no ORM unless the schema forces it): library snapshot, version history, folder-structure record, cover library, canvas boards, etc.
- **Frontend:** server-rendered **Jinja templates + vanilla JS**, no SPA framework. Richer interactive JS only where a feature needs it (e.g. the org canvas) — settle those specifics in that feature's spec.
- **Env:** `venv` + `requirements.txt`.
- v1 is read-only. Fill in remaining choices (charts, etc.) as features are specced. Never assume an unstated version or library.

Each lettered step becomes its own `/symr-plan` session and its own spec; landed steps stay, marked ✅ DONE and pointing at the spec that is authoritative for what actually shipped (read that spec, never the roadmap summary, before touching landed work). It also carries dated measurements that shouldn't be re-derived. Its sibling `docs/Planning/feature_ideas.md` is the loose backlog the roadmap draws from — ideas, not commitments.
- `app.py` — Flask app factory. Page routes (`/` home, `/canvas`, the **entity pages** `/song/<id>` / `/version/<id>` / `/recording/<id>` / `/release/<id>` (four `@app.route` decorators on **one** view function, each supplying its tier) / `/track/<id>` / `/album/<id>` / `/artist/<id>` / `/playlist/<id>` (`?generation=1` renders the generation view, `?tier=` toggles it) / `/search`, `/dev` dev-tools landing, `/dev/snapshot`, `/dev/canonical*`, `/dev/artists`, `/dev/import`, `/dev/roundtrip`, `/dev/generations*` (including the plain form-POST `/dev/generations/confirm`, no JS), and stubs `/audit`, `/covers`, `/folders`, `/analytics`), OAuth (`/login`, `/callback`), `/api/*` endpoints, an app-wide `before_request` login guard (exempts `login`/`callback`/`static`), and centralized error handlers (`HTTPException` + `Exception`) that render `error.html` for pages and JSON for `/api/*`.
- `config.py` — every setting, read from the environment via `.env` (python-dotenv): Spotify credentials / redirect / scopes, `DB_PATH` (`SYMR_DB_PATH`), the spotipy token-cache path, `APP_PORT` / `APP_DEBUG`, `MAX_CONTENT_LENGTH`, and `SECRET_KEY` (random per process unless `SYMR_SECRET_KEY` is set, which is what keeps sessions valid across a restart). Credentials live in the environment only — never hard-code or log them.
- `spotify_client.py` — the only place an authed Spotify client is built: `get_auth_manager()` (OAuth, scopes from config, on-disk token cache) and `get_spotify_client()` (returns `None` when there's no valid cached token). Its custom `requests` session sets `respect_retry_after_header=False` so a 429 raises immediately instead of blocking for an hours-long app-quota `Retry-After` — `snapshot.py`'s `_call()` handles the wait itself. Scopes are read-only.
- `jobs.py` — the one background-job slot. A single module lock guards a single `_active` job name, so claiming the slot is one atomic check-and-set (`try_start`) with no lock ordering and no race — `snapshot.py` / `history_import.py` / `roundtrip.py` no longer own job locks of their own. Also owns cooperative stopping (`request_stop` / `stop_requested` — a flag the job polls at its own safe points, never a kill), `now_iso()`, the `RateLimited` fail-fast wrapper `call(status, fn, …)` that every Spotify request in every job goes through, and `JobStatus` (per-job progress fields + a capped 200-entry event log; `running` is *derived* from `jobs.active()`, never stored).
- `db.py` — SQLite `SCHEMA` + additive migrations (`_migrate`) + `VIEWS`. Library metadata is normalized: `track`, `album`, `artist`, plus `track_artist` / `album_artist` join tables carrying per-credit `position`; each of `track`/`album`/`artist` also keeps a verbatim `raw_json` of the Spotify object. `membership` is the append-only per-playlist log; `snapshot` is per-playlist state (including the `excluded` flag that skips item reads on repeat pulls). `artist_alias` / `reviewed_artist_pair` resolve Spotify's duplicate artist ids. `play` is the imported streaming history with `play_import` as its per-run log — a play resolves to a track through the **`played_uri_track`** view (no FK, no stored "foreign" flag), which unions `track.uri` with `track_uri_alias` so relinked uris resolve too; `track_uri_alias` maps a requested uri onto the track Spotify substituted for it, `roundtrip_failed_uri` remembers what couldn't be resolved, and `roundtrip_run` is the round-trip's per-run log. `VIEWS` is dropped and recreated whenever its definition changes — `_ensure_views` compares a hash of it against `meta.views_hash`, so an edit always takes effect while an ordinary restart needs no write lock (a rebuild can't take one while a pull is mid-transaction). It holds the artist read path: `resolved_track_artist` / `resolved_album_artist` (alias-resolved), `track_artist_credit`, `track_artist_role` (primary vs featured), and `track_artists` (the rendered display string) — **`track.artists` is write-only, never read**. `generation` (docs/specs/generations-B.md) is one row per current-favs playlist, `ordinal` **stored**, not derived from sort order; `snapshot.generation_declined` mutes the new-generation prompt for a playlist Finn said no to; `generation_presence` (DISTINCT-joined against `membership`/`track_group`) is what `generations.py` derives tenure from at query time. `wanted_uri` (docs/specs/entity-pages-K.md §6) is the album page's queue of tracklist uris with no `track` row, merged into the round-trip's existing work list rather than being a second queue; `album.tracklist_json` / `tracklist_pulled_at` and `artist.image_url` / `detail_pulled_at` cache the entity pages' one-request-per-first-view detail fetches — kept **out of `raw_json`**, which a snapshot pull overwrites with the simplified object embedded in every track.
- `snapshot.py` — the library snapshot engine: pulls playlists and their contents from Spotify into the append-only `membership` log and the normalized `track`/`album`/`artist` tables. Full-pull / refresh / backfill entry points, a background thread + module-global status dict, and a request counter. **Read-only w.r.t. Spotify — nothing here ever writes to the library.** It also owns the **shared track-ingest path** (`_usable_track` / `_parse_track_item` / `_upsert_track_full`): `roundtrip.py` calls the same three rather than growing a second way to write a track, so changing their signatures breaks it.
- `history_import.py` — play-history ingestion: extracts a Spotify GDPR streaming-history export zip into `data/streaming_history/<timestamp>/` and parses its JSON into `play`, deduped by a SHA-1 `row_hash` over 16 named source keys. Also owns the coverage counts the page reads, on the two bases step D split apart: **known to Symr** (a `track` row exists) vs **in your library** (that track also has a `membership` row). No Spotify API requests anywhere in it.
- `roundtrip.py` — **the only module that writes to the Spotify library.** Resolves played-but-unknown uris into real `track` rows by **replacing** the private `<Play History Loader>` scratch playlist's contents with 100 uris at a time and reading the full track objects back out of the playlist-items endpoint. Two invariants are load-bearing and were both learned the hard way: **replace, never append** (so the read is always `offset=0` and no running offset can drift), and **read the page as a bag, never as a sequence** — a track identifies itself by its own id, and a substituted one carries `linked_from` naming what was requested, so `track_uri_alias` is written *only* from `linked_from`, never inferred from position. Every run starts with a guard (name + owner verified live, zero writes if either is wrong); a 400'd batch is narrowed with the off-quota `open.spotify.com` probe, uris that don't come back are found by set difference, three consecutive failed batches trip a breaker, and each batch commits before the next begins. A **reconciliation pass** then retries what didn't come back — Spotify substitutes some ids without setting `linked_from`, and that pairing is auto-aliased only when the normalized full title *and* the album artist both match what the export recorded; anything less is flagged `needs a manual alias` rather than guessed (`roundtrip_failed_uri.reason` decides what is worth re-requesting: a probe-confirmed 404 never is). Those leftovers get a plain pick-a-track table on the page, whose candidates match on the normalized title *base* only — looser than the automatic rule on purpose, since that is what a human is there to judge. Writes no `membership` rows and runs no detection. The loader playlist id is a hardcoded constant with a `TODO` until the next full pull makes it pickable. `_WORK_LIST_SQL` has a second `UNION ALL` arm for `wanted_uri` (album-tracklist uris, `plays=0` so they sort after every played one); **"done" stays derived** — a wanted uri is finished when it resolves through `played_uri_track`, exactly like a played one, so nothing is checkpointed and nothing goes stale.
- `artists.py` — artist identity: per-track alias-resolved id sets for detection (`artist_sets`), plus duplicate-candidate detection and the merge/unmerge curation writes. Owns `artist_alias` / `reviewed_artist_pair` only.
- `canonical.py` — the four-tier (`release` → `recording` → `version` → `song`) canonical-grouping engine, plus the viewer read paths (`song_groups`, `representative`, `tier_counts`, and the tier-agnostic `subtree` / `group_tree`, of which `nested_tree` / `song_tree` are now thin song-tier wrappers). `artist_credits_for_tracks` is the batched `{track_id: [{artist_id, name}]}` lookup every page linking individual artist names uses — `track_artists` / `track_display`'s `artists` is a pre-joined display string with no id to link to. Owns `canonical_group` / `track_group` / `reviewed_pair` and never touches `track` or `membership`. `apply_partition` takes a **`cleanup` keyword**: `False` skips the four `_cleanup_tier` passes, which are a full `canonical_group × track_group` join each and dominate the cost of a batch — only a caller that runs `cleanup_all_tiers()` itself afterwards may pass it. **None of its functions commit — callers own the transaction.**
- `canonical_detect.py` — detection for that engine: proposes candidate groups and pre-filled tier labels from normalized titles, suffix classification (`base`/`version`/`recording`/`neutral`, keywords matched as whole token sequences against `normalize_suffix`), and a duration tolerance. Also builds the cross-artist queue's buckets and decides the deterministic auto-group rule. Reads `pending_tier_review` (the cross-artist assignments owing a version/recording/release pass, written by `/api/canonical/cross/apply`, keyed on track id because group ids get reconciled away) — **`pending_song_ids` owns the "group still has ≥2 members" filter**, so the count on `/dev/canonical` and the items `?queue=pending` serves can't disagree. Decides nothing and writes nothing — pure computation over `track`/`membership`, no Spotify calls.
- `canonical_autogroup.py` — the write side of that auto-group rule: closes every qualifying queue item in one batch of `apply_partition(cleanup=False)` calls, logs the run in `auto_group_run`, and takes a whole-table snapshot of `track_group`/`canonical_group`/`reviewed_pair` beforehand so undo is a wholesale restore. One level deep — a new run replaces the snapshot. Unlike `canonical.py`, these functions **do** commit.
- `grouping.py` — the org canvas's proximity/chained card grouping (`group_cards`) and the export-text renderer (`render_export_text`) behind `/api/export`. Pure geometry over card/label coordinates; no DB, no Spotify.
- `generations.py` (`docs/specs/generations-B.md`) — generations and **tenure**, deliberately distinct from membership: `generations()` / `tenures()` derive everything at query time from `generation_presence` (nothing materialized), take a `tier="version"|"song"` parameter (a whitelisted column lookup, never interpolated), and both read-only, never commit. `pending_new_generation()` / `confirm_generation()` / `decline_generation()` own the confirm-on-pull flow for new `vXX.Y.Z` playlists; callers commit those. `presence_for_tracks()` gives the ordinals a track set was present in (the strip every entity page renders) and `runs()` is the public run-collapsing helper `tenures()` uses internally. Read-only over `track`/`membership`/the canonical tables and makes no Spotify calls.
- `entities.py` (`docs/specs/entity-pages-K.md`) — the entity pages' read paths that belong to no existing owner: `play_stats` (total / past 30d / past 7d over a track set, resolved through **`played_uri_track`** so relinked uris count; a window whose start predates `MAX(play.ts)` returns `None`, which renders `—` rather than a lying `0`) and `playlists_for_tracks`. Also the two guarded detail fetches — `fetch_album_tracklist` / `fetch_artist_image` — which spend **at most one Spotify request, on that entity's own page, on first view only**, swallow every failure so the page still renders from the DB, and never page past the first 50 tracklist items. The album fetch queues unowned uris into `wanted_uri` rather than writing partial `track` rows. Read-only w.r.t. the Spotify library.
- `templates/` — Jinja templates. `base.html` (shared shell: navbar + content block; `body_class` block for the immersive full-viewport pages); `_macros.html` (shared macros — `datetime_span`, which emits the `data-datetime` span `format.js` renders; `generation_confirm_banner`, the new-generation yes/no form shared by `/dev/snapshot` and `/dev/generations`; and K's four: `play_stats`, `entity_link` — **the one way to link any entity, so links can't drift page to page** — `artist_names`, and `generation_strip`, extracted from `generations_tenure.html` so the tenure table and the entity pages share one implementation); `home.html`; `canvas.html` (org canvas, extends base); `dev.html` (dev-tools landing page); `snapshot.html`; the entity pages `entity_group.html` (one template for all four tiers), `entity_track.html`, `entity_album.html`, `entity_artist.html`, `entity_playlist.html` and `search.html`; `canonical.html` (canonical-tracks viewer), `canonical_review.html` (the immersive review queue), `canonical_cross.html` (the reworked cross-artist queue); `artists.html` (duplicate-artist curation); `history_import.html` (play-history upload + coverage); `roundtrip.html` (the foreign-track round-trip: controls, live event feed, failed uris, run history); `generations.html` (the 37 generations: span, group counts, carried/new split), `generations_tenure.html` (the tenure table: one row per version/song group ever present, a 37-cell strip of real `<td>`s per row); `coming_soon.html` (shared stub placeholder for `/audit`, `/covers`, `/folders`, `/analytics`); `error.html` (generic HTTP error page, extends base).
- `static/css/style.css` — the single stylesheet (navbar, shared page styles, canvas).
- `static/js/` — one vanilla-JS file per interactive page, each an IIFE, no bundler: `format.js` (site-wide relative-time rendering of any `data-datetime` span), `snapshot.js` (pull/refresh/backfill controls, status poller, progress bar, request counter — **also the per-playlist exclude toggle**, which is why `entity_playlist.html` includes it), `canonical_review.js` + `canonical_viewer.js` + `canonical_cross.js` (the canonical-tracks review queue, viewer, and cross-artist queue), `artists.js` (duplicate-artist merge/unmerge), `history_import.js` (export upload, import progress, live coverage), `roundtrip.js` (start/stop controls, status poller, live event feed), `canvas.js` (the org canvas).

## Keep It Simple
- KISS. The goal is code that is **done, understandable, and works** — not production-grade or clever. AI tends to overdo complexity; don't. Reach for the simplest thing that fully solves the problem.
- **Security is the one exception to KISS — never do the bare minimum here.** Everything security-related must be done *fully and properly*, not just "right": secure coding practice (never leak tokens/secrets) **and** the implementation of things like login, auth, and session handling. Do those thoroughly.
- The other hard requirement: never corrupt or wrongly modify my real Spotify library. Beyond security and that, favor simplicity over robustness — the rest just needs to be done right.

## Git Workflow
Solo repo, single checkout at `/Users/finne/Projects/Spotify-Manager` (no worktrees). Branch prefixes: **`feat/`** features, **`chore/`** tooling/docs, **`fix/`** fixes. A feature branch carries both the spec (its first commit) and the implementation commits stacked on top.

These are **always-on tripwires** — warn *before* acting, then do whatever I decide. Never silently proceed past one; never refuse once I've answered.
1. **No committing to `main`.** Before any commit, check `git branch --show-current`; if it's `main` and this isn't a tiny main-level fix, stop and flag it — the work belongs on a branch.
2. **Confirm the branch before new work.** A fresh session inherits whatever branch was last checked out, which is likely wrong for new work. Confirming the branch is the *first* action of any new phase, before reading code: check `git branch --show-current`, propose a fresh branch off up-to-date `main` (or a switch to the right existing one), wait for my OK, then dive in.
3. **No premature merge/push.** Merging a branch into `main` and pushing happen only in the Verify finish-up — never during Plan or Implement.

Commits: commit only when I ask, in logical units — one for the spec, a few for implementation as needed, optionally one or more from verify. Commit in my name only — no Claude/AI co-author or attribution line. **Don't push without being asked.** The sanctioned merge+push is the Verify finish-up: a **`git merge --ff-only`** into `main` (keeps history linear, no merge-commit clutter) then push. This repo is solo and single-copy, so `--force-with-lease` is safe when a rewrite is the agreed fix.
